# PKG-2 account namespace replay review

This gate tests the two-interruption witness from
[the replay model](PKG2_REPLAY_BUDGET_MODEL.md) against actual mounted EXT4/JBD2
and `account_redo.c`. It does not change the production account protocol or
implement a package grant.

## Fixture and interruption boundary

The private directory is exactly the existing 1 MiB `E4_DIR_MAX`, with dense
allocated mappings. Its first block has dot entries, three free 24-byte slots
interleaved with the three original 16-byte canonical account entries. All other
space consists of legal 12-byte free records and distinct, exactly sized 16-byte
filler entries with real inodes and one link each. Neither offers enough room
for a publication name. This preserves the model's exclusion geometry without
inode aliases, a reduced kernel limit, or unsupported four/eight-byte free
records. Linux validates the completed seed before any account operation.

The account stages and pending record are generated by actual redo. The host
adapter substitutes only a selected write callback: it calls the same actual
`e4_jcreate_account` used by `e4_ac_write`, releases the empty node, syncs, and
returns EIO before writing the contents. The process freezes/closes the image;
the next invocation freshly prepares the actual journaled mount. This selects a
durable empty-create boundary that the real callback can leave between its
separate creation and data transactions. It is a deterministic protocol-prefix
test, not physical power loss or a failing flush simulation.

Each geometry/sector pair has an uninterrupted control and this sequence:

1. Update publishes passwd/group, creates empty shadow.publish, then stops.
2. Fresh recovery publishes passwd, creates empty group.publish, then stops.
3. Fresh recovery cannot create passwd.publish: EFBIG at the real directory
   size limit. Repeat within that mount and assert zero additional sector writes.
4. Remount and repeat the same blocked recovery and zero-write retry assertion.

The byte profile uses synthetic validation and three 8 KiB payloads. This tests
the filesystem/backend/redo path, not admission by the real account service.
There is no package operation, concurrent writer, live pin or privilege probe.

## Evidence boundary

Run from Linux/WSL at the repository root:

```sh
python3 scripts/test_pkg_account_namespace.py
# or: make test-pkg-account-namespace-host
python3 scripts/test_pkg_account_namespace_observer.py .codex-remote-attachments/pkg-account-namespace-YYYYMMDD-HHMMSS
```

The runner copies the C/header/include/Python inputs to a private workspace,
compiles with ASan/UBSan and strict warnings, creates only private regular-file
images, and retains images, source hashes, logs and Linux byte dumps. Reads use
a host memory mirror; every accepted write also updates the private image and
sync flushes it. All runtime filesystem and redo sources remain unchanged.

Linux e2fsck checks each seed and terminal image. Debugfs verifies exact canonical
and staging bytes, both empty later temporaries, pending-record continuity,
root ownership/modes and the unrelated sentinel. The first temporary is absent.
The control checks all canonical bytes and absence of publication temporaries.
Whole-image equality across remounts is not asserted: mount/journal/sync state
can change. Zero-write retry claims apply to the second recovery call after
the first blocked call has been synced in the same mount.

The separate read-only observer verifies directory checksums, records exact
account inode/slot positions and slack lengths, enumerates initialized block and
inode bitmap bits, and reconciles group totals with the superblock. UNINIT
bitmaps have no valid stored bits: their implicit reserved allocation counts are
reported from group descriptors, without inventing physical bit positions. These are
snapshots, not a complete attribution of every allocation delta to one account
object or a production ownership validator. It checks image hashes before and
after observation and requires the primary campaign to have passed.

## Results, 2026-10-21

Accepted evidence: `.codex-remote-attachments/pkg-account-namespace-20261021-132851/`.
Actual-code ASan/UBSan and Linux audits: **30/30 terminal states PASS**, across
1/2/4 KiB blocks and 512/4096-byte sectors. These comprise six uninterrupted
controls, twelve durable empty-create interruptions and twelve blocked remounts.
Each blocked process also repeats recovery after sync: **12/12 retries return
EFBIG with zero additional sector writes**. Thus 24 recovery calls explicitly
observe the blocked error. All three seed files also pass Linux e2fsck.

The corrected observer passes **30/30 image observations**. Each pair has one
publication-sized slot after the first interruption and zero after the second.
The later empty temporaries occupy the remaining large slots. Both blocked
remounts retain zero such slots and unchanged canonical/stage/pending bytes.

| Block size | Free blocks at blocked state | Free inodes | Suitable publication slots |
| --- | ---: | ---: | ---: |
| 1024 | 27045 | 996 | 0 |
| 2048 | 13514 | 996 | 0 |
| 4096 | 6750 | 1764 | 0 |

Both sector sizes have the same counts. These are ample free raw resources;
the refusal is namespace capacity, not exhaustion of the existing account floor.
The primary manifest's inventoried C/header/include/Python sources all compare
unchanged after the run. The separately added observer has its own retained
source/hash; its image hashes compare unchanged before/after observation. This
is not a whole-repository, shared-media or firmware-preservation claim.

Retained failures/partial attempts:

- `pkg-account-namespace-20261021-132404`: Linux rejects the eight-byte free
  record seed before account operations; no behavior result accepted.
- `132531`: deliberately stopped during the first stdio-read control due to
  excessive host I/O; no terminal control/witness accepted. The successor uses
  a memory read mirror with every write still persisted to the image.
- `132703`: uninterrupted C control and Linux fsck pass, but sentinel mode audit
  fails (debugfs inherited 0777 rather than the expected 0644). The successor
  explicitly seeds 0644. Original INCOMPLETE manifests/logs remain unchanged;
  separate qualification files identify why these attempts are not accepted.
- Accepted campaign's `observer-first-failed.py` fails allocation-total
  reconciliation by treating UNINIT bitmaps as valid bits. The original source
  and failure explanation remain beside corrected `namespace-observer.py` and
  `namespace-observations.json`. No image mutation or allocation claim came from
  that failed observer.

`git diff --check` and opt-in target dry-run pass. There is no fresh Ring 3,
BIOS/UEFI/SMP, physical or release-media result in this campaign. The earlier
private stack matrix and its separate preservation checks retain their own scope.

## Consequences and next design gate

Raw block/inode headroom and one-pass allocation bounds do not establish
restart-safe namespace capacity. A package grant cannot be admitted on that
basis alone. The existing fail-closed account recovery path must retain pending
and staging evidence rather than expose the mixed canonical generation.

Before enabling package mutation, specify either a namespace profile whose
remaining publication capacity survives all admitted restarts, or a separately
reviewed persistent capacity mechanism. Admission must validate actual record
geometry, ownership and all allowed competing writers. A one-pass dry run is
insufficient. The dynamic remaining-resource model also needs refinement to
actual planner peaks, pools and journal recovery.

Cleaning all publication temporaries before restarting publication is a
candidate protocol change to review, not an implemented remedy or a proof of
general progress. It must preserve authoritative stages/pending, classify
partial and foreign objects, and survive every cleanup/publication interruption.
It would not alone establish package grant isolation or bounded pool admission.

Boot acceptance, source preservation and media preservation remain separate.
This host gate does not rerun the earlier private Ring 3 firmware matrix, build
release media, provision trust, enable installation, or write a physical disk.
