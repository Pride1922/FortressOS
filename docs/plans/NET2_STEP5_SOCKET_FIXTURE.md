# Step 5 prerequisite: bounded synthetic TCP socket-backend fixture

2026-10-02. Step 4 boundary: f925aa1. The prerequisite below was frozen before
implementation. The peer, independent audit and runner now exist; executed
gates and remaining qualifications are recorded in [Step 5](../roadmap/net2-step5.md).

## Existing infrastructure and missing pieces

scripts/test_net_tcp_client.py and test_net_tcp_server.py currently cover only
QEMU user networking: independent SLIRP TCP with Linux socket applications.
At the Step 4 boundary there was no synthetic TCP socket-backend runner. Existing test_net_eth.py,
test_net_icmp.py and test_net_udp.py demonstrate UDP-carried raw Ethernet
injection, ARP emulation and outbound pcap audit; they do not implement TCP
sequence/ACK/retransmission/FIN behavior.

Reuse that backend shape:

```
-netdev socket,id=net0,udp=127.0.0.1:<host-port>,localaddr=127.0.0.1:<guest-port>
```

Host receives guest Ethernet frames on a bound loopback UDP socket and sends
injected Ethernet II frames to the QEMU endpoint. This is not a TCP socket relay
or packet injection through filter-dump. Frames omit Ethernet FCS and include
minimum Ethernet padding. Use existing guest IP 10.0.2.15, emulated gateway/peer
10.0.2.2 and documented PEER MAC; answer validated ARP requests explicitly.
Kernel remains polling, using its existing worker/wait/timer mechanisms.

## Modules and independence

Add scripts/net_tcp_socket_peer.py for the bounded host peer and
scripts/test_net_tcp_matrix.py for orchestration; keep existing user runners
usable. Peer must implement Python wire encoding/checksum and sequence logic
independently of FortressOS TCP codecs/engine. Audit outbound captures in a
separate parser/checksum/stream-reconstruction pass; peer state PASS or injection
logs alone must never satisfy a wire gate. Record a JSON injection/action trace
for diagnosing intended faults, alongside serial log and pcap.

### Golden wire reference

Use committed hand-computed RFC wire vectors as the normative golden reference,
not bytes generated by the peer, kernel, or audit implementation. Before coding,
write tests/fixtures/net_tcp_wire_vectors.json and a calculation worksheet with
literal complete Ethernet/IPv4/TCP hex and explicit offsets, lengths, padding,
pseudo-header words, one's-complement sums/carries and final checksums. Cover SYN
with/without MSS, SYN/ACK, pure ACK, odd-length data, FIN/ACK, RST/ACK and a
sequence-wrap example. RFC 791/9293 define layout and RFC 1071 defines checksum
arithmetic. The worksheet's independently derived expected values are reviewed
before either implementation uses them; expected bytes must never be regenerated
by the code under test. Check encoder output byte-for-byte, and decoder/audit
fields against literal expectations. A real Linux peer capture may supplement
interoperability evidence later; it is not required as the golden source and
must not be relabeled hand-computed. The vectors now exist with the companion
NET_TCP_WIRE_WORKSHEET.md; neither peer nor audit generates the expected file.

### Peer/audit code-sharing boundary

Peer and audit share no protocol helpers: no Ethernet/IP/TCP encode/decode,
checksum, sequence comparison, ACK/state logic or stream reconstruction code.
Peer uses its own implementations; audit implements its own independent parser
and checksum arithmetic. The audit must not import the peer module, and the
peer must not import the audit. Both read the same immutable golden vectors.
Only scenario constants, expected application patterns/lengths and orchestration
utilities may be shared: they specify inputs/requirements rather than decide
whether wire behavior is correct. The audit can reuse the existing pcap-container
reader from test_net_rings.py, which extracts raw records without TCP parsing;
the peer operates on UDP Ethernet datagrams and does not use that reader.
Tests must corrupt a checksum/header and falsify a peer PASS status to establish
that the independent audit still rejects the captured wire behavior.

### Failure artifacts and termination lifecycle

Create a unique persistent build/net2-step5/<run-id>/<case>/ directory BEFORE
starting QEMU. Write serial.log, qemu-stderr.log, wire.pcap, injection.jsonl and
peer-events.jsonl directly there, not in a TemporaryDirectory copied afterward.
Save argv.json, scenario.json (seed/profile/ports/addresses/limits), versions.txt,
golden-vector hash, and final result.json with error/traceback, last peer state,
byte counts/hashes, process exit status and any audit failure. On failure retain
the exact test ISO/config and disposable UEFI vars for reproduction; these are
artifacts, never user data disks. Explicitly record artifacts not yet created.

In finally, stop injection, flush host event writers, request QEMU termination,
wait a bounded three seconds, then kill and wait if needed. Close/reap QEMU
before final pcap audit so normal exit can finish its capture file; preserve raw
pcap even if it has a truncated final record. Flush/fsync host logs and the final
manifest; report write failures instead of converting the case to PASS. Never
delete the persistent case directory on failure. SIGINT/timeout paths must run
the same lifecycle. Test forced case failure, timeout and QEMU crash to verify
artifacts remain after process termination and no QEMU process remains alive.

This guarantees retention of files already written for ordinary handled case
failures/QEMU termination, without relying on successful post-termination copying.
It cannot guarantee QEMU's unflushed tail after SIGKILL, or data after disk-full,
host crash or power loss; record incomplete evidence explicitly. The guarantee
is exercised by the runner's --retention forced-failure/timeout/crash gate.

Implement only the two finite test roles, not a general host TCP stack:

| Role | Handshake | Data and close |
| --- | --- | --- |
| Passive peer, guest client | Observe guest SYN, choose fixed test ISN, synthesize SYN/ACK, require valid final ACK. Repeat SYN/ACK for duplicate SYN or handshake retry. | Consume guest request and ACK cumulatively; after guest FIN/complete request, send finite response, FIN and await ACK. Guest tcptest/nc must return exact bytes and EOF. |
| Active peer, guest listener | Inject SYN, validate guest SYN/ACK, inject final ACK; allow deterministic delayed/dropped ACK and duplicate SYN. | Send finite request while draining guest finite-server echo, or consume nc listener's stdin before providing response. Validate guest FIN, ACK it and complete peer FIN without conflating half-close with application exit. |

Each role tracks a full four-tuple, local ISN/snd_una/snd_nxt, peer ISN/rcv_nxt,
advertised receive window, retained unacknowledged bytes, SYN/FIN sequence units
and explicit state. SYN/FIN consume one sequence unit; pure ACK consumes none.
Use modulo-32-bit comparisons with an explicit half-range ambiguity rejection.
Reject ACK beyond submitted snd_nxt and tuple mismatch. Exact duplicate payload
must not append bytes twice; overlapping retransmitted bytes must match. Bound
and explicitly reassemble allowed out-of-order injections; cumulatively ACK
only contiguous bytes, never a gap. Never infer ACK progress from host time.

Default offer MSS 536, separate MSS 1460 and omitted-MSS cases; do not negotiate
window scaling, SACK, timestamps or ECN. Accept plain SYN/ACK declining an ECN
offer in a targeted active-peer case. Respect the guest's advertised window;
do not synthesize unlimited data merely because the host UDP socket accepts it.
Use valid independent IPv4/TCP checksums, total/header lengths, byte order,
IP addresses, MAC direction and Ethernet padding on every ordinary injection.

## Finite resource and timing budgets

At most eight peer connection records per case; four pending guest-listener
tuples for backlog tests. Each peer record has at most 8192 outstanding payload
bytes, 32 retained segment records and 8192 bytes of OOO state. Generate the
known 65536-byte patterns by offset and hash consumed bytes; do not retain an
unbounded transcript or spawn a thread per packet. Cap injection trace at 20000
events, total case packets at 20000 and total application bytes at 65536 each
way per connection. Limit fault/retry schedule to eight retransmissions per
retained segment and at most 120 seconds per traffic case. Reject exhaustion
as fixture failure rather than silently dropping audit evidence.

Drive host peer deadlines with monotonic time and explicit finite event-loop
timeouts. Guest ticks stay real: no timer/quiet-time bypass. Client cases allow
the existing 120-second reboot quiet period with a separately bounded 180-second
warm-up; listener cases can start immediately. Loss tests must wait for actual
observed guest retransmission and inspect its sequence/bytes, not assume a timer
fires exactly when the host wakes. Always terminate QEMU and close sockets on
failure; save artifacts before temporary fixture removal.

## Deterministic profiles and audit requirements

Start with clean 64KiB client request/response and finite-server streaming echo,
including partial sends, sequence wrap, half-close and shell recovery. Then add
named fault profiles, no randomness needed:

- Drop one SYN/ACK or final handshake ACK; validate bounded handshake retry.
- Drop one data segment/ACK, duplicate one and swap two bounded segments;
  verify ordered exactly-once bytes, valid cumulative ACKs and retransmission.
- Advertise zero window, then reopen it; validate bounded probes and resumed
  data without new-byte acceptance inferred from a probe.
- Lose FIN or its ACK; require valid retransmission/EOF and finite teardown.
- Inject a wrong-tuple, corrupt-checksum and out-of-range ACK segment; require
  no corresponding data delivery or acknowledgment beyond valid sequence space.
- Fill four listener entries with half-open/completed children, duplicate a
  SYN and exceed the cap; complete a non-head child, expire a half-open and
  prove new ingress can recover. Record the actual 30-second guest deadline.

The implemented auditor checks both directions in QEMU filter-dump capture
order, matching socket-backend inbound bytes against the independent injection
log. QEMU capture time and host wall time are different clock domains (a one-hour
offset was observed under WSL), so they are never merged to infer ACK ordering.
This also proves only captured delivery, not that a UDP send alone reached RX.
Guest outbound pcap audit independently checks Ethernet/IP/TCP lengths,
checksums/options/padding, full tuples, valid handshake, initial sequence-relative
payload offsets, identical retransmissions, exact finite bytes/hash, cumulative
ACK bounds and SYN/FIN sequence accounting. Check both application directions
using guest-visible output plus peer consumption and audited outbound ACKs;
outbound-only pcap cannot prove every injected frame reached the guest. Save
injection trace separately and label intentional invalid inputs. Refusal/reset
and timeout fixtures must distinguish an observed RST from runner timeout.

## Step 5 order and matrix gate

1. Unit-test the independent peer's wire vectors, wrap/ACK accounting, duplicate
   handling, OOO bounds, resource exhaustion and finite deadline behavior.
2. Gate one BIOS/e1000 socket case for both guest-client and guest-listener roles
   with existing tcptest/tcpserve, before implementing nc. Run clean profile,
   then named fault profiles; stop on unexplained capture/state disagreement.
3. Implement planned finite nc and test numeric client/listener pipelines with
   short writes, stdin EOF -> SHUT_WR, buffered RX -> EOF/reset and prompt return.
4. Run BIOS/UEFI x e1000/e1000e x {user,socket}: eight SMP=1 cases, each proving
   both directions. Add BIOS/UEFI e1000 BSP-tool SMP=4 smoke and AP direct-dispatch
   rejection, explicitly distinguished from Ring 3 AP socket support.
5. Rerun client regression fence and UDP/ICMP/ring/absent-NIC regressions. Retain
   listener rollback/signal/reference gates and Step 4's kind-capture regression.

Use disposable ISO/OVMF copies, exact argv preflight with negative unsafe-storage
tests, and no data disks. Complete matrix is the Step 5 acceptance gate, not
merely a runner capable of naming eight cases. Synthetic peer evidence
complements the independent SLIRP user backend; neither establishes physical
wire/DMA acceptance or general TCP conformance. Physical Step 6 stays separate.
